# 重复提问收敛：在途合流 + 短窗答案重放

> 状态：设计定案（2026-07-25，两轮 AskHuman 评审），**未实现**。
> 实现分支：`feat/ask-coalesce`（worktree `../HumanInLoop-ask-coalesce`，Dev Instance popup-only）。
> 依赖 / 复用：`docs/specs/daemon-architecture.md`（请求登记表与 Coordinator 汇聚点）、
> `docs/specs/reply-history.md`（历史只在汇聚点记一次）、`docs/specs/todo-whats-next.md`
> （待办出队发生在首个终态回答）。

## 1. 问题

用户在 Cursor 里收到**两张内容完全相同的提问卡**（普通 Ask 与 whats-next 都出现过），
不回答时还会继续叠加。2026-07-25 的排查结论：

- **AskHuman 从不主动重发**。每一张卡都对应一次真实的 `AskHuman` 命令调用。
- 触发源在 Agent 侧：等待人类回答期间那一轮（turn）被中断（手动打断、
  `User aborted request`、`Connection failed repeatedly` 等；本项目全部 Cursor
  transcript 里非正常结束共 32 次）。中断后 agent 恢复时认为上一问没送达，**原样重发**。
- 放大器在 AskHuman 侧：Cursor 中断 turn 时**不杀** `AskHuman` 进程，daemon 因此收不到
  CLI 断开（`request … cli disconnected; cancelling` 在这些时段一次都没出现），旧卡片
  继续有效。用户回答旧卡时，答案写进一个**已无人读取的 stdout**，agent 永远看不到，
  于是下一轮继续重发。

实测两例：

| 时间 | 事件 |
| --- | --- |
| 07-25 09:43:16 | 请求 `0b15b341` accepted |
| 07-25 09:47:35 | 用户回答，daemon 记 done、写入历史——但调用方那一轮早已死亡 |
| 07-25 09:47:47 | 请求 `46c34b78` accepted，内容与前者逐字相同 |
| 07-25 09:48:53 | 用户被迫再答一遍 |

| 时间 | 事件 |
| --- | --- |
| 07-24 21:54:59 | 请求 `370a9cfc` accepted（6 问决策卡，飞书） |
| 07-24 22:06:00 | 请求 `8c15e6d6` accepted，同一张卡的第二份，两卡并存 15 分钟 |
| 07-24 22:21:32 / 22:21:34 | 用户连着答了两次 |

## 2. 需求

Agent 侧的中断与重发不在我们的控制范围内，AskHuman 要做的是**让重复的调用不产生重复的
打扰**：

1. **旧卡还在等你回答时**：新的相同提问**绑定到旧卡**，不再弹新卡。你答一次，新旧两个
   调用方同时拿到这份答案。**绝不作废旧卡**——你可能正填到一半，任何替换都会丢内容。
2. **旧卡你已经答完时**：短时间内到来的相同提问**直接返回上次的答案**，完全不打扰你。
3. **指纹不同就照旧弹两张**：这是两个不同的问题，不能合并。

## 3. 设计定案

### D1 会话键：agent session 优先，MCP 实例兜底

合流与重放都以**会话**为隔离边界，键取值顺序：

1. `TaskRequest.agent_session_id`（非空）；
2. 否则 `TaskRequest.mcp_instance_id`（同一个 MCP server 进程即同一个 agent，足够稳）。

两者都为空（纯人工 CLI 调用、脚本调用）→ **完全不参与**合流与重放，行为与现状一致。
理由：脚本可能故意连续问同一个问题，吃掉重复会造成语义错误。

### D2 指纹：全量精确匹配

指纹覆盖一次提问的**全部可见与行为要素**，逐字一致才算相同：

- 共享 message 文本 + 展示附件的绝对路径列表（有序）；
- 每个问题的文本 + 其预定义选项（文本、`recommended` 标记、`todoId`，有序）；
- 全局模式位：`is_markdown`、`select_only`、`single`、`output_format`、`whats_next`。

归一化只做一件事：**去掉文本首尾空白**。不做相似度匹配、不忽略 message 差异——
两次 whats-next 的固定问题相同而完成报告不同，宽松匹配会把它们错误合流。

不进指纹的字段：`source`、`lang`、`project`、`caller_pid`、`perf_id` 等与提问内容无关的
传输字段。

### D3 合流：绑定到旧卡，界面零变化

同会话存在**在途**请求且指纹相同时：

- 不创建新请求、不弹新卡、不向 IM 投放、不触发 `ask-received` 用户 hook
  （合流本质是「同一次提问」，hook 语义为每接收一次提问恰触发一次）；
- 新调用方作为 **follower** 挂到既有请求上，等待同一份终态结果；
- 已显示的卡片**不做任何改动**：不加角标、不加计数、不刷新——用户可能正在输入；
- daemon 日志记一条合流记录（含被复用的 request id 与 follower 数量）。

托盘待答数、`/watch` 的「正在等待你的回答」、Agent 快照的 `waitingRequestId` 都只反映
这**一个**请求，不因重复调用虚增。

### D4 引用计数取消：所有等待者都走了才取消

现状是「提交请求的 CLI 断开即取消整个请求」。合流后改为引用计数：

- 每个绑定在请求上的调用（原始 + 各 follower）算一个等待者；
- 单个等待者断开只做计数减一，卡片保持有效；
- **计数归零**才执行原有的取消路径（IM 卡定格「已被调用方取消」、弹窗关闭、
  `state.registry.remove`）；
- 终态结果产生后，广播给**所有仍在的等待者**，各自写自己的 IPC `final`。

### D5 重放缓存：每会话最近一条，5 分钟窗口，仅内存

- 每个会话键只保留**最近一条**已完成问答：`{ 指纹, RenderOutcome, 完成时刻 }`；
- 全局上限 **64 个会话**，超出按 LRU 淘汰；
- 有效窗口 **5 分钟**，过期即视为未命中，正常弹新卡；
- 只存在 daemon 内存里。daemon 重启 / 排空换新后缓存丢失，行为退化为正常弹卡——
  这是可接受的边界，不做持久化。

### D6 只有真实回答进缓存

进缓存的条件是**用户真的答了**（终态 `ChannelAction::Send`）。以下一律不进缓存：

- 用户取消（`[status]`）——取消的语义是「重新问我」，重放会把 agent 卡进死循环；
- 调用方取消、系统取消、无可用渠道、弹窗拉起失败等所有非用户作答的终态。

### D7 重放结果携带显式说明，复用 `status`

重放返回的不是一份「假装刚发生」的答案，必须让 agent 知道它拿到的是旧答案。载体**复用
既有的 `status`**，不新增区块或字段——`status` 的语义本就是「这次请求的状态说明」，
文本侧已经承载「用户取消」与「用户未回答此问题」两种情况：

- 文本输出：在所有结果区块**之前**加一个 `[status]` 区块，正文按 `lang` 本地化，
  说明「这是你 N 秒前提出的完全相同问题的回答，用户已经答过，本次没有再打扰他」；
- JSON 输出：`status` 字段填同一句话（该字段此前只在取消时出现，本次起扩展为通用状态说明）；
- MCP：`ask` 为文本透传（spec mcp.md D5 二轮定案），`[status]` 区块随文本直达模型，无独立字段；
- 其余内容（`[selected_options]` / `[user_input]` / `[files]` / 多问题的 `# Qn` 分组、
  whats-next 的纯文本形态、JSON 的 `answers`）与原答案逐字一致，退出码一致；
- 说明文案到此为止，**不**追加「想要新回答就改提问再问」之类的指引。

配套的语义澄清（必须同批改，否则文档会误导 agent 把重放当成取消）：

- `--agent-help` 里 `[status]` 那一行改为通用表述（中英各一处），不再写「用户取消时出现」；
- `cli/output.rs` 的 `JsonOutput.status` 字段注释改为通用状态说明，并写明**判断是否被取消
  要看 `action`**，不能用「`status` 是否存在」来判断（MCP `ask` 已为文本透传，无独立字段）；
- 重放时 `action` 保持「作答」语义（JSON 为 `answer`），只有真正的取消才是 `cancel`。

### D8 副作用只发生一次

- **回复历史**：合流只记一条（历史写在 Coordinator 汇聚点，与等待者数量无关）；
  重放不经过 Coordinator，**不再记一条**，`--show-last` 仍能查到原始那条。
- **待办出队**：同理只在首个终态回答时发生一次。重放把同一条待办再交给 agent 是正确的
  ——agent 没收到过答案，也就没执行过那条待办。
- **用户 hook `ask-received`**：合流与重放都不触发。

### D9 竞态：终态已产生时不许再挂

新提问到达的同一瞬间，旧请求可能刚被答完（Coordinator 已出终态、登记表尚未清理）。
此时**不得**把 follower 挂上去（它永远等不到结果）。判定与挂载必须在同一把锁内完成：
已进入收尾的请求视为「不在途」，转由重放路径处理（此时缓存可能还没写入，则退化为
正常弹新卡）。

### D10 不留开关

行为是纯收敛（少一次重复打扰），默认始终生效，不加配置项、不加 experimental 开关。

### D11 契约不变

- CLI 一行不改：它拿到 `Accepted` 后只等 `Final`，不关心 request id；
- stdout 结果区块、退出码 0/1/3、配置兼容契约全部不变；D7 不新增区块或字段，只是让既有
  `status` 多承载一种状态；
- 合流时回给 follower 的 `Accepted` 携带**被复用的** request id。

## 4. 不做的事

- 不作废、不替换、不修改任何已显示的卡片（用户明确否决）。
- 不做跨会话去重：不同 agent 会话问出相同问题是正常的。
- 不做模糊 / 相似度匹配（D2）。
- 不改 Agent 侧行为，也不试图让 Cursor 中断时杀掉 CLI 进程。
- 不持久化重放缓存（D5）。

## 5. 验收

1. 同一会话连发两次逐字相同的提问：只出现**一张**卡；答一次后**两个**调用都拿到同样的
   结果与退出码；历史只增加一条。
2. 第一次调用被 kill（模拟 Cursor 杀进程）后，卡片仍在（还有 follower 在等）；两个调用
   都断开后，卡片按原有路径定格为已取消。
3. 答完后 5 分钟内发起相同提问：不弹卡，输出最前带一个说明重放的 `[status]` 区块
   （JSON 为 `status` 字段），其余内容与上次逐字一致；超过 5 分钟：正常弹卡。
4. 上一次是用户取消：不重放，正常弹卡。
5. message 差一个字：弹两张卡，互不影响。
6. 无 agent session、无 MCP 实例 id 的调用：连发两次相同提问 → 两张卡（行为同现状）。
7. whats-next 场景与普通 Ask 表现一致；被重放的待办不会被二次出队。

## 6. 反馈意见（2026-07-25，计划评审）

- **不要作废旧卡**：初版方案里「新提问自动作废同会话旧卡」被否决——旧卡可能已经填到一半，
  作废就把输入弄丢了。改为绑定到旧卡（D3），只有指纹不同才弹两张。
- **重放标注复用 `status`，不新增区块/字段**：`status` 表达的是「系统状态」，目前只有取消
  一种用例只是现状使然，语义上并不专属取消。据此改写 D7，并同批澄清 help / JSON / MCP 三处
  字段说明。
- **JSON 与文本在「未作答」上的表达差异**（JSON 靠条目缺席、文本靠 `[status]` 文案）
  本次不动，要统一另开一件事。
