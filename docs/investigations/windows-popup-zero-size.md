# Windows 弹窗客户区变为 0×0（issue #13）

## 复现基线

- 日期：2026-09-07。
- 系统：Windows 11 Home 24H2 x64（10.0.26100），真实登录桌面，单显示器、100% 缩放。
- 虚拟化：Intel Mac 上的 Parallels Desktop 18.1.1，系统盘为 SATA 0:3。
- 版本：GitHub 最新正式发布版 [v0.13.0](https://github.com/Naituw/AskHuman/releases/tag/v0.13.0)，
  使用官方 `AskHuman-x86_64-pc-windows-msvc-v0.13.0.zip`，不是测试机上原有的开发安装。
- 发布包 SHA-256：`e594243b01022aeb4ce4ea2eefacc532281d4e76bbf0b4a6f7310a8feb51e1ff`。
- 解压后 EXE SHA-256：`acc2cf91d0b9c206e6c1d40989bc5fa3e8542f4fa2dc55f3608c1fea8bc42b98`。
- 独立 `ASKHUMAN_HOME`，仅启用 Popup，`rememberSize=true`，初始尺寸为 560×620。

## 最小复现步骤

1. 启动一个普通提问，等待弹窗显示。开启预热时再等热 helper 就绪。
2. 将该弹窗最小化，保持请求未完成。
3. 此时读取 `config.json`：`channels.popup.width` 和 `height` 均变为 **0**。
4. 发起第二个普通提问。
5. 第二个弹窗已经显示、没有最小化，但原生 `GetClientRect` 为 **0×0**，正文和回答区不可用。
6. 恢复第一个窗口，配置重新变为 560×620；第二个窗口仍为 0×0，不会自动修复。

原生桌面自动化通过 `ShowWindowAsync(SW_MINIMIZE/SW_RESTORE)` 执行最小化/恢复，
通过 `EnumWindows`、`IsWindowVisible`、`IsIconic`、`GetClientRect` 采集窗口状态；
只识别测试 EXE 所属、标题为 AskHuman 的窗口，排除 IME 等辅助窗口。

开启预热连续两次复现，关闭预热也复现。热路径的第二次请求在 perf 日志中有 `dmn.assigned`，
确认领用了预热 helper。**预热不是必要条件，也不需要依赖不可控的并发竞争。**

| 阶段 | 配置尺寸 | 第一个窗口 | 第二个窗口 |
|---|---|---|---|
| 首次显示 | 560×620 | 可见、560×620 | 未创建 |
| 第一个最小化 | 0×0 | 已最小化、客户区 0×0 | 未创建 |
| 再发起提问 | 0×0 | 仍最小化 | 可见、未最小化、客户区 0×0 |
| 恢复第一个 | 560×620 | 可见、560×620 | 仍为 0×0 |

## 根因与修复边界

`app/mod.rs` 的旧 `persist_popup_size` 把所有 `Resized` 事件当作用户尺寸变化，直接读取
`inner_size()` 并写回共享配置。Windows 最小化时读到 0×0；下一次 `finalize_popup_show`
未经校验就调用 `set_size(0, 0)`，冷、热路径均受影响。建窗时的 `min_inner_size` 没有阻止
此处程序调用把已创建窗口设为零。

修复在 `app/popup_size.rs` 统一恢复尺寸并记录本窗口恢复基线；窗口创建和上屏共用有效尺寸。
记忆入口过滤未上屏、隐藏、最小化、最大化、收尾、过期和无效尺寸事件，并忽略与程序恢复基线
相同的回调，防止另一个 helper 的尺寸偏好被旧恢复值覆盖。记忆开关从最新配置读取。
已污染的配置在使用时恢复为可用窗口，正常调整窗口后写回有效尺寸。

这里证实的是错误尺寸导致无法作答；尚无证据证明发生了线程锁死。

## 修复版验证

修复版使用 v0.13.0 标签源码及其 Cargo.lock，仅覆盖本次修改的 `app/mod.rs` 并加入
`app/popup_size.rs`，与正式发布版做同一套原生窗口步骤对照。
通过 `scripts/install-windows.cmd` 构建并安装至隔离目录，安装后的 EXE SHA-256 为
`18bfe32f9a06d5c3b7151ee26867e05b2553edb8603fa94b7a9f1ca987cf6c99`。
没有覆盖测试机原有安装或带未提交改动的开发目录。

| 场景 | 官方 v0.13.0 | 修复版 |
|---|---|---|
| 预热开启，最小化后再提问（各两轮） | 配置与第二个窗口均为 0×0 | 配置与第二个窗口保持 560×620 |
| 预热关闭，最小化后再提问 | 配置与第二个窗口均为 0×0 | 配置与第二个窗口保持 560×620 |
| 初始配置已是 0×0 | 首个窗口可见但为 0×0，20 秒内未恢复 | 首个和后续窗口均恢复为 560×620 |
| 调整至 700×800，再最大化 / 恢复、发起第三个请求 | 此项未测试 | 配置始终记住 700×800，恢复和第三个窗口均为 700×800 |

污染配置的恢复发生在读取使用时，不立即改写磁盘；这一行为避免程序恢复事件再次覆盖
其他窗口刚保存的尺寸。最小化窗口自身报告 0×0 是正常的 Windows 行为，断言针对配置和
后续**未最小化**窗口。

macOS 和 Windows 的 4 项尺寸定向单元测试均通过。macOS 已执行安装脚本，并由用户确认
显示、调整尺寸、最小化/恢复和回答正常。Windows 原生验证仅覆盖上述单屏环境，未扩展为
多屏或多 DPI 发布验收。Windows 五组用例全部完成，关闭测试弹窗后没有遗留可见测试窗口。

原始 `result.json`、CLI 输出和 perf 日志保留在测试机
